Taming Stockfish in Node.js: Asynchronous UCI Streams and Time-Based Depth

Integrating a chess engine into a Node.js backend isn’t like calling a standard REST API. You don’t send a POST request and get a JSON response. Instead, you communicate via the Universal Chess Interface (UCI), a text-based protocol that relies on standard input and standard output streams.

When building the backend for ChessX, I had to wrap Stockfish’s asynchronous, streaming stdout into clean, resolvable Promises, while also solving a very human problem: engine depth vs. human clock time.

The UCI Protocol and Stdout Streams

When you send a go depth 12 command to Stockfish via stdin, the engine doesn’t just sit silently and return the answer. It continuously prints info lines to stdout, updating you on its current search depth, principal variation (PV), and centipawn evaluation. Finally, it prints a bestmove line.

If you just attach a generic onmessage listener, you’ll get flooded with partial evaluations. We only want to resolve our Promise when the engine has finished calculating the exact depth we requested and has output the final bestmove.

async function sendSF(cmd, depth) {
  engine(cmd); // Send command to Stockfish stdin

  if (depth) {
    return new Promise((resolve) => {
      const payload = { info: '', bestmove: '' };
      const previousHandler = engine.onmessage;
      
      // Intercept the stdout stream
      engine.onmessage = (msg) => {
        // Capture the info line for the specific depth we requested
        if (msg.startsWith(`info depth ${depth}`)) {
          payload.info = msg;
        } 
        // Resolve only when the engine declares the bestmove
        else if (msg.startsWith('bestmove')) {
          payload.bestmove = msg;
          engine.onmessage = previousHandler; // Restore previous handler
          resolve(JSON.stringify(payload));
        }
      };
    });
  }
}

By temporarily hijacking the onmessage handler and filtering for the specific depth string, we turn a messy continuous stream into a clean, asynchronous function call.

The Time-Based Depth Problem

In classical chess, you can tell Stockfish to calculate to depth 25. It might take 10 seconds, but that’s fine. In Bullet or Blitz chess on Chess.com, taking 10 seconds to find a move means you will “flag” (lose on time) before you even make the move.

A static depth limit is useless for real-time play. The engine’s calculation depth must be dynamically tied to the human player’s remaining clock.

Dynamic Depth Allocation

I implemented a formula in the content script that reads the player’s clock DOM element, converts it to seconds, and calculates a safe depth limit before sending the request to the Node server.

let mySecLeft = timeStrToSec(timesDivs[getMyTeamColor()].innerText);
// Allocate 1 depth ply for every 5 seconds on the clock, capped at depth 12
lastDepth = payload.depth = Math.min(Math.floor(mySecLeft / 5), 12);

Why this formula?

  1. The Divisor (5 seconds): This ensures that if you have 5 seconds left, the engine searches to depth 1 (instant). If you have 60 seconds (1 minute), it searches to depth 12. It scales linearly with the time you have to physically move the mouse.
  2. The Cap (12): On a standard CPU, Stockfish NNUE reaching depth 12 takes roughly 0.5 to 1.5 seconds. Capping it ensures that even if you have 5 minutes on the clock in a rapid game, the extension remains snappy and doesn’t lock up the UI waiting for a depth 30 evaluation that the human wouldn’t understand anyway.

Configuring the Engine

To make the engine behave consistently, it needs to be configured via UCI setoption commands upon server startup.

function configureStockfish() {
  sendSF("setoption name Hash value 4096"); // Allocate 4GB RAM for transposition tables
  sendSF("setoption name Ponder value true"); // Allow thinking on opponent's time
  sendSF("setoption name Skill Level value 20"); // Maximum strength
  sendSF("setoption name Move Overhead value 30"); // Compensate for network/WebSocket latency
}

The Move Overhead parameter is critical in a WebSocket architecture. It tells the engine to assume that a few milliseconds will be lost in network transit, preventing the engine from flagging in timed games hosted on the server side.

The Takeaway

Interfacing with legacy or native binaries in Node.js requires treating standard I/O streams as asynchronous event queues. By wrapping UCI stdout in Promises and dynamically coupling engine depth to the user’s real-world constraints, you can build a bridge between brute-force silicon calculation and human gameplay.
